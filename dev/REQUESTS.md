# 사용자 요청 및 작업 메모

이 문서는 AIPF를 실제로 사용하며 발견한 문제, 개선 요청, 앞으로 할 일을 사용자 원문으로 보존한다.

## 작성 원칙

- 사용자는 형식 없이 짧게 적어도 된다.
- AI는 사용자 원문을 요약하거나 바꾸지 않는다.
- AI는 작업을 시작하기 전에 대상 항목과 작업 범위를 사용자에게 확인한다.
- 완료된 항목도 삭제하지 않고 상태만 변경한다.

## 빠른 메모

떠오르는 내용을 아래에 그대로 적는다. 우선순위와 해결 방법은 나중에 정한다.

1. 실제 사용 해보니 P_000이랑 로드맵만 생성 후 나머지 plan은 차후 생성하려고 함. 그러고 다른 세션에서는 이를 인지 못하고 유일한 plan인 P_000이 종료되었으니 프로젝트가 종료되었다고 판단함.
==> 2가지 방법을 적용하고자 함. 첫 번째는 aipf init 이후 첫 세션은 무조건 프로젝트 전체 계획 및 설계에 대한 내용만 다루는 세션으로 국한. 두 번째는 사용자가 처음에 정리된 명세서를 제시하고, 이에 맞춰서 자잘한 내용을 다루는 식으로 구현해야 할 듯. 따라서 명세서를 정의할 필요가 있음. 이에 대한 내용은 뒤에서 다룸
2. handoff가 난무할 것을 대비해 관리 객체를 두어 이를 다루려고 했는데, 관리 객체는 말 그대로 todo list와 같은 형태가 되고 AI가 별도로 작업 예정를 생성함.
==> 각 작업 예정을 구조화 해서 생성하게 할 것인지, 관리 객체를 좀 더 상세하게 작성하고 관리 객체만 사용하게끔 강제할 건지 정할 필요 있음. 특히 evidence와 같이 AI가 항상 작성하는 자료의 경우 관리 객체로 지정해두는게 좋을듯.
3. git을 사용하기로 했으므로, task 등 작업 이후 commit를 통해 수행하기 이전으로 되돌리는 기능도 추가하면 좋을듯. 다만 되돌릴 때 해당 작업에 대한 로그는 생성해야함.
4. 기존에 사용자가 제공하는 원본 자료 등은 /docs에 저장하기로 했는데, 이 중 소스 코드가 포함될 수도 있음. 따라서 이름을 /inputs로 다루는게 적합해보임. /inputs 안에서 /codes, /docs 등 분류하는 걸로.
5. 작업 진행하다 보면 task, plan이 변경되는 경우가 잦음. 이 때 변경된 작업을 old 등에 두고 저장할 필요가 있을까? 의논 해봐야 할듯.
6. 사용자가 할 작업을 한 문서, 즉 명세서로 정리를 해두자. AI랑 대화하면서 매번 이 문서, 저 코드 이렇게 지정하기 보다 해당 명세서에 관련된 내용을 미리 정리해두는 것이 좋을듯. 사용자도, AI도 해당 문서 하나만 보고 전체 과정, 목표, 참고 자료 등을 쉽게 파악할 수 있게. 다만 이 문서는 AI는 읽기만 가능하고, 수정은 안되게끔. 이상한 부분이 있으면 사용자가 직접 수정하는 걸로. 이 명세서는 어떤 템플릿이 있으면 좋을 것 같음. 템플릿에 어떤 내용들이 들어가야할 지는 추가 논의 필요.
7. 폴더 구조를 지 맘대로 씀. Memory_map.md를 만든 의미가 별로 없음. 좀 더 강하게 통제할 필요가 있음.
8. 사용자의 의도를 완전히 파악을 못하는 경우가 있음. 다만 이는 그럴 수 있는데, 이를 사용자가 인지 못하는 경우 문제가 생김. 따라서 Plan 단위로는 AI가 실행하기 전에 어떤 식으로 뭘 수행할지, Task 단위로 끝나고 뭘 했는지 좀 더 자세히 보고하는 체계가 필요하다고 느낌.

## 요청사항

새 요청은 `R-001`부터 번호를 붙인다.

### R-001: 프로젝트 전체 수명주기와 초기 계획 구분

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: 빠른 메모 1번
- 문제: 유일한 Plan이 완료되면 후속 Plan 예정이 있어도 AI가 프로젝트 전체를 완료로 판단한다.
- 원하는 결과: 프로젝트 전체 계획·설계와 개별 Plan의 완료를 구분한다. 초기 세션의 역할과 사용자 명세서 기반 진행 방식을 정의한다.
- 관련 항목: R-006
- 결정 및 진행 기록: 초기 설계 세션은 `PROJECT_SPEC.md`와 전체 Roadmap만 정의하고 Plan을 실행하지 않는다. 이후 새 세션은 직전 Plan 객체, Task 결과, 필요한 Audit과 명세서의 진행 계획을 읽어 다음 Plan을 제안하고, 사용자 승인 후 그 Plan 하나만 완료까지 수행한다. 완료된 Plan 세션은 다음 Plan을 생성하지 않는다. 명세와 실제 결과가 충돌하면 사용자에게 확인한다. 마지막 Task 승인 후 프로젝트는 `awaiting_plan`으로 돌아가며 완료된 Plan ID를 보존한다. 다음 Plan은 새 ID로 생성되고, 모든 단계 종료 후 `aipf project complete`로 사용자가 프로젝트 완료를 별도 확정한다. 전체 tests 9개와 CLI 생성 예시 검증 통과.

### R-002: 작업 예정과 관리 객체의 역할 정리

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: 빠른 메모 2번
- 문제: handoff 대응용 관리 객체와 AI가 별도로 만드는 작업 예정이 중복되어 todo list가 늘어난다.
- 원하는 결과: 작업 예정의 구조화 수준을 정하고, 관리 객체를 단일 기준으로 강제할지 결정한다. Evidence처럼 AI가 항상 작성하는 자료의 저장 위치도 정한다.
- 관련 항목: R-005, R-008
- 결정 및 진행 기록: 별도 TODO, Handoff, Knowledge, 영구 Session 객체는 만들지 않는다. 프로젝트 전체 예정은 `PROJECT_SPEC.md` Roadmap, 승인된 실행은 Plan·Task, 중요한 사용자 결정은 선별적 Audit이 담당한다. Task 제출마다 append-only Evidence 객체를 생성해 실제 요약·변경·산출물·검증과 제출 시점의 미완료·결정 필요 사항을 보존한다. Task는 최신 `remaining`, `decisions`와 모든 `evidence_ids`를 유지한다. 후속 작업은 반드시 Task `remaining`에 기록하며 다음 Plan 세션이 이를 확인한다. 재제출 Evidence 이력과 손상 객체 검증을 포함한 전체 tests 14개 및 CLI 생성 예시 검증 통과.

### R-003: Plan 실행 단위 Git checkpoint와 복원

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: 빠른 메모 3번
- 문제: Plan 에이전트가 구분한 실행을 Git에 원자적으로 남기고, 확인된 실행 상태로 안전하게 돌아가는 공식 절차가 없다.
- 원하는 결과: 실행 checkpoint를 Plan 및 Task와 연결하고, checkpoint ID로 기존 이력을 보존하며 복원하고, 복원 사유를 기록한다.
- 관련 항목: R-005
- 결정 및 진행 기록: checkpoint는 Task 단위가 아니라 Plan 에이전트가 구분한 실행 단위이며 여러 Task를 포함할 수 있고 같은 Task가 여러 checkpoint에 참여할 수 있다. `P_XXX-C_XXX` ID를 Plan의 `checkpoints`와 Git commit 메시지에 함께 기록한다. 생성 시 선택 Task의 선언 산출물, Plan 색인, 관련 Task·Evidence·Audit, runtime과 `PROJECT.md`를 한 commit에 담고 추가 실행 경로는 명시적으로 지정한다. 소유가 확인되지 않은 변경이나 기존 staged 변경이 있으면 중단한다. 복원은 clean working tree에서만 수행하며 대상 checkpoint 상태를 `git reset` 없이 새 commit으로 재현한다. 기존 checkpoint 색인과 append-only Evidence·Audit 이력은 보존하고, 대상과 사유를 새 Audit에 기록한다. Git 저장소·초기 commit·checkpoint 유일성과 조상 관계를 검증한다. checkpoint 생성·복원 및 안전 차단을 포함한 전체 tests 19개 통과.

### R-004: 사용자 입력 디렉터리를 `inputs/`로 개편

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: 빠른 메모 4번
- 문제: 사용자 원본에 문서뿐 아니라 소스 코드도 포함될 수 있어 `docs/`라는 이름이 범위를 충분히 표현하지 못한다.
- 원하는 결과: 사용자 원본을 `inputs/`에 저장하고 `inputs/codes/`, `inputs/docs/`처럼 유형별로 분류한다.
- 관련 항목: R-006, R-007
- 결정 및 진행 기록: 기존 `docs/` 호환 없이 `inputs/docs/`, `inputs/codes/`, `inputs/data/`, `inputs/media/`로 교체함. `inputs/`는 사용자 소유·AI 읽기 전용이며 `ref/`는 AI가 수집한 외부 원본에 사용함. tests 6개와 생성 예시 검증 통과. 사용자 승인 완료.

### R-005: Plan과 Task 변경 이력 보존 방식

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: 빠른 메모 5번
- 문제: 진행 중 Plan과 Task가 바뀔 때 이전 버전을 보존할지 정해지지 않았다.
- 원하는 결과: Git, Audit, 별도 `old/` 저장 방식의 역할을 비교하고 단일 변경 이력 정책을 정한다.
- 관련 항목: R-002, R-003
- 결정 및 진행 기록: 별도 `old/`와 객체 `revision`을 사용하지 않는다. 이전 파일 내용은 Git, Task 수행 시도는 Evidence `attempt`, 수정 요구는 Task `feedback`, 후속 작업은 `remaining`, 중요한 변경 이유는 선별적 Audit이 담당한다. Plan 에이전트가 구분한 한 번의 실행이 끝날 때 Git checkpoint를 만들며 한 실행은 여러 Task를 포함할 수 있다. Plan의 `checkpoints`가 `{id: P_XXX-C_XXX, task_ids: [...]}` 형식으로 중앙 색인을 보존한다. 실제 hash 대신 checkpoint ID를 commit 메시지와 공유해 같은 commit에 Plan 색인을 원자적으로 포함한다. 일반 review의 자동 Audit을 제거하고 `--audit-summary`가 지정된 중요한 결정만 기록한다. 실제 Git commit 생성과 복원은 R-003 범위다. checkpoint 구조와 선택적 Audit을 포함한 전체 tests 16개 및 CLI 생성 예시 검증 통과.

### R-006: 읽기 전용 사용자 명세서와 템플릿

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: 빠른 메모 6번
- 문제: 목표, 전체 과정, 참고 자료가 여러 대화와 파일에 흩어져 사용자와 AI가 매번 다시 지정해야 한다.
- 원하는 결과: 사용자가 관리하고 AI는 읽기만 하는 단일 명세서와 작성 템플릿을 정의한다.
- 관련 항목: R-001, R-004, R-008
- 결정 및 진행 기록: `inputs/PROJECT_SPEC.md` 하나를 자연어 Markdown 기준 문서로 사용함. Roadmap은 최소 단계 목록을 포함하며 항목 하나가 Plan 하나의 기본 후보임. 사용자가 승인하면 항목을 합치거나 나눌 수 있음. AI는 기본적으로 읽기만 하고 사용자 명시 요청이 있을 때 수정 가능함. 명세서가 없거나 진행 계획 단계가 없으면 `plan apply`를 차단함. tests 7개와 생성 예시 검증 통과. 사용자 승인 완료.

### R-007: 파일 생성 위치 규약과 배치 변경 동기화

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: 빠른 메모 7번
- 문제: AI가 `MEMORY_MAP.md`의 폴더 규칙을 충분히 참고하지 않고 임의 위치에 파일을 만들 수 있으며, 파일 배치가 바뀔 때 관련 규약·구현·예시가 서로 달라질 수 있다.
- 원하는 결과: 파일 유형별 canonical 위치와 소유권·생성 주체·용도를 생성 규약으로 명확히 한다. 배치를 변경할 때는 `dev/PROJECT_DIRECTION.md`의 canonical layout, `MEMORY_MAP.md`, 생성 템플릿 `AGENTS.md`와 README의 경로 안내, 관련 코드와 테스트, CLI로 생성한 `example/`을 같은 작업에서 함께 갱신한다.
- 관련 항목: R-004
- 결정 및 진행 기록: `MEMORY_MAP.md`와 canonical layout을 기준으로 생성 위치를 안내하고, 위치가 불명확하면 임의 디렉터리를 만들지 않고 사용자에게 확인한다. 배치 변경은 규약 문서만의 변경으로 끝내지 않고 경로를 담은 `AGENTS.md`, `MEMORY_MAP.md`, README, `SKILLS.md`, `PROJECT_SPEC.md`, 관련 구현·테스트·CLI 생성 예시까지 동기화한다. 자동 스캔, 규칙 밖 쓰기 차단, 파일 자동 삭제·이동, 별도 allowlist 시스템은 추가하지 않았다. 생성 규약 검증을 포함한 전체 tests 12개와 CLI 생성 예시 검증 통과.

### R-008: Plan 실행 전·Task 완료 후 상세 보고

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: 빠른 메모 8번
- 문제: AI가 사용자 의도를 잘못 이해해도 사용자가 실행 전까지 이를 발견하기 어렵다.
- 원하는 결과: Plan 실행 전에는 수행 방법과 범위를 상세히 보고하고, Task 완료 후에는 실제 변경과 검증 결과를 상세히 보고한다.
- 관련 항목: R-001, R-002, R-006
- 결정 및 진행 기록: Plan은 Roadmap 단계, 자동 기록된 직전 Plan, 수행 방법, 위험·주의점과 기존 목표·범위·Task·완료 조건을 승인 전에 보고한다. Task 결과는 요약, 실제 변경, 산출물, 검증 근거, 미완료·알려진 문제, 사용자 결정 필요 사항을 보존하고 승인 전에 보고한다. 검증하지 않은 항목을 성공으로 보고하지 않으며 계획과 실제가 다르면 숨기지 않는다. 별도 Report나 Evidence 객체는 추가하지 않았다. `PROJECT.md`는 승인 대기 중인 핵심 판단 정보를 표시한다. 전체 tests 11개와 CLI 생성 예시 검증 통과.

### R-009: Plan 실행 흐름 투영

- 상태: 완료
- 우선순위: 미정
- 사용자 원문: "task랑 evidence는 빼고, 흐름만 파악하면 되니까 Plan, checkpoint, Audit 단위만 두자."
- 문제: Task와 Evidence까지 흐름에 표시하면 `PROJECT_FLOW.md`가 빠르게 커져 Plan 진행과 주요 결정의 흐름을 파악하기 어렵다.
- 원하는 결과: Plan, checkpoint, 중요한 Audit, 현재 runtime 위치만 보여 주는 간결한 흐름 문서를 둔다.
- 관련 항목: R-003, R-005, R-007, R-008
- 결정 및 진행 기록: 루트의 `PROJECT_FLOW.md`는 Plan, checkpoint, material Audit, runtime의 읽기 전용 투영으로 사용하고 Task와 Evidence는 표시하지 않는다. 관리 객체가 원본이며 CLI가 상태 변경 후 마커 내부만 재생성한다. 마커 밖의 안내·범례는 보존하며, 사용자나 에이전트가 생성 영역을 직접 수정하지 않는다. Task 대상 Audit은 소속 Plan에 연결하고, 복원 Audit은 대상 checkpoint에서 연결한다. checkpoint 생성·복원 commit에도 최신 흐름을 포함한다. 전체 tests 23개와 CLI 생성 예시 검증 통과.
