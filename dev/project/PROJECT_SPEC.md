# AIPF 프로젝트 명세서

> 이 문서는 AIPF 자체 개발의 목표다. 배포할 빈 명세는 `template/project/PROJECT_SPEC.md`이며 두 문서는 독립적이다.
> AI는 기본적으로 읽기만 한다. 사용자 명시 요청으로 수정할 때 이전 명세를 `dev/project/old/`에 순번으로 보존한다.

## 1. 개요

### 프로젝트 이름

AIPF — AI Project Framework

### 목표

대화 기록이 없어도 Markdown 문서와 Git으로 목표, 현재 상태, 변경 이유와 검증 결과를 이해하고 AI 프로젝트를 이어갈 수 있는 틀을 제공한다. 사용자는 배포본을 clone한 뒤 별도 AIPF 설치 없이 사용할 수 있어야 한다.

### 최종 산출물

- `template/`: 사용자 프로젝트에 제공할 독립된 Markdown 틀
- 루트 라우팅과 `dev/`: AIPF 자체 목표·개발 규칙·상태·기록·자료
- `template/`만 `release` 루트로 내보내는 최소 배포 도구

### 완료 기준

- 개발자와 사용자가 서로 다른 목표·상태·자료를 읽는다.
- 에이전트가 계획, 구현 지시, 검증, 최종 완료 확인을 구분한다.
- 배포 트리가 승인된 main의 template 트리와 정확히 일치한다.
- 개발 기록과 자료는 사용자용 배포본에 포함되지 않는다.

### 제외 범위

이전 Python CLI 복원, 기존 프로젝트 자동 변환, 상주 서비스, Telegram 대화·응답 처리, 프로젝트별 기술 스택 선결정.

## 2. 참고 자료

- 현재 사용자 지시: AIPF 개발과 적용 자료 분리, 개발용 README 제거, template-only release 배포, 혼자 로컬에서 사용하는 최소 구현
- `dev/archive/2026-09-27-markdown-redesign/`: 현재 Markdown 구조의 의도와 검증 기록
- Git의 `0729a72` 이전 `dev/PROJECT_DIRECTION.md`, `dev/REQUESTS.md`: 과거 개발 자료. 현재 요구사항으로 자동 재도입하지 않는다.
- 개발 참고 자료는 `dev/inputs/{docs,codes,data,media}/`, 재사용 검증 정보는 `dev/knowledge/`에 관리한다.

## 3. 배경

Markdown 중심 개편은 설치 부담을 없앴지만 개발 자료와 배포 틀이 같은 루트에 놓였다. 개발 에이전트가 빈 사용자 명세를 AIPF 목표로 읽고, 개발 완료 기록이 새 사용자 프로젝트에 포함되는 문제가 생겼다.

대상은 AIPF를 개선하는 개발자와 AIPF로 자신의 프로젝트를 수행하는 사용자다. Change는 합의된 범위의 변경 하나이며 프로젝트 전체 완료와 구분한다.

## 4. 제안하는 방식

- 개발은 root AGENTS와 `dev/instructions/`를 따르며 `dev/project/`의 목표·상태를 읽는다.
- 배포할 문서와 빈 폴더는 `template/`에서 관리한다. 내부 경로는 배포 후 프로젝트 루트를 기준으로 쓴다.
- 개발 중 template 지침을 현재 운영 지침으로 실행하지 않는다.
- main은 개발 원본, release는 template에서 생성한 사용자 배포본이다. release에 직접 수정하지 않는다.
- README는 `template/README.md`만 둔다. 개발 절차는 루트 AGENTS와 `dev/instructions/`로 안내한다.

루트 전체를 배포하면 개발 상태와 사용자 상태를 다시 혼동하므로 명시적인 두 영역을 선택한다.

## 5. 구현 명세

### 최소 구현 원칙

AIPF 자체는 혼자 로컬에서 사용하는 프로젝트다. 사용자 요구에 필요한 최소 동작부터 구현하고 실제 사용에서 필요가 드러날 때만 늘린다. 무결성 검사, 예상만으로 추가하는 오류 감지·동시성·일반 복구 코드와 이를 위한 대규모 테스트는 기본 범위에 넣지 않는다. Git 등 도구의 기본 실패 처리를 사용하고 바꾼 정상 동작을 직접 확인한다. 이 원칙을 AIPF로 수행하는 사용자 프로젝트의 제약으로 강제하지 않는다.


- 목표와 현재 상태, 활성 Change와 Handoff, 완료 archive, 자료와 검증 정보를 파일로 유지한다.
- 구현은 사용자의 명시적인 시작 지시 후 수행하며 관련 없는 개선은 포함하지 않는다.
- Git 이력과 완료 태그로 분기·복귀하며 기존 이력을 되돌리거나 강제 push하지 않는다.
- 사용자 프로젝트는 하나의 실행 진입점과 버전별 소스·누적 실행 결과를 관리한다. AIPF 배포 도구는 사용자 소스 공간과 구분한다.
- 배포 입력은 clean main에 커밋된 template tree다. 출력 release root tree는 입력 tree와 정확히 같아야 한다.
- 개발 자료, 로컬 Flow, 자격 증명은 배포하지 않는다. Telegram 자격 증명은 환경 변수에서만 읽는다.
- 원격 분기, 소유권 불명확, 검증 실패는 성공으로 보고하지 않으며 상태를 보존하고 원인을 보고한다.

## 6. 검증 방식

- 바꾼 문서와 실제 파일 위치, 개발/사용 역할을 확인한다.
- 독립된 공격·방어 검토와 주 에이전트의 근거별 판정
- 임시 로컬 Git 저장소에서 template 배포와 기존 release 연결이라는 정상 동작을 직접 확인한다. 상시 무결성 검증 도구나 과한 오류 시나리오 테스트는 두지 않는다.
- 사용자가 최종 완료를 확인한 뒤 main 병합·태그·게시 및 release 배포

## 7. 진행 계획

1. Markdown 중심 틀 전환 — 완료. 기록은 `dev/archive/2026-09-27-markdown-redesign/`.
2. AIPF 개발과 사용자 템플릿 분리, 문서 정리, 최소 template-only release 배포 — 현재 Change.
3. 이후 개선은 실제 사용에서 드러난 필요를 사용자와 합의해 별도 Change로 정한다. 추가 기능은 아직 확정하지 않는다.
