# 법정 검토 모델

## 1. 역할

- 적대적 검토자 2명: 결함, 누락, 위험, 완료 조건 위반을 독립적으로 찾는다.
- 변호자 2명: 제출물의 타당성을 독립적으로 입증하고 지적에 답한다.
- 심사자 1명: 제출물과 네 주장을 비교해 구조화된 판결을 낸다.

각 역할은 다른 역할의 숨은 추론이나 대화 원문을 받지 않는다. 제출물, 완료 조건, 제약, 검증 증거, 공개된 구조화 주장만 받는다.

## 2. 실행 조건

- `high`, `critical`: 필수
- `medium`: 프로젝트 설정에 따름
- `low`: 오케스트레이터 검토

코드 실행, 보안, 공용 인터페이스 변경은 최소 `medium`으로 본다. 정책 엔진은 위험도를 올릴 수 있지만 낮출 수 없다.

## 3. 절차

1. 오케스트레이터가 case manifest와 증거 snapshot을 고정한다.
2. 두 검토자가 서로 독립적으로 주장한다.
3. 두 변호자가 주장과 증거를 바탕으로 독립적으로 답한다.
4. 심사자가 `approved`, `changes_required`, `rejected`, `user_decision_required` 중 하나를 판결한다.
5. `rejected` 또는 `changes_required`면 개선 task를 생성하고 재심사한다.

재심사는 최대 3회다. 한도 이후 `user_decision_required`로 전환한다.

## 4. 주장 구조

각 주장은 주장 ID, 대상 완료 조건, 심각도, 설명, 증거, 재현 방법, 제안 조치를 포함한다. 변호는 주장 ID별로 인정, 반박, 부분 인정 중 하나를 선택하고 증거를 연결한다.

## 5. 판결 구조

판결은 상태, 충족한 완료 조건, 미충족 조건, 채택·기각한 주장과 이유, 필요한 수정, 잔여 위험, 신뢰도를 포함한다.

오케스트레이터는 판결을 임의로 무시할 수 없다. 정책 예외가 필요하면 사용자 결정을 기록한다.

## 6. 독립성 보호

- 동일 세션을 복수 역할에 재사용하지 않는다.
- 가능하면 서로 다른 모델 또는 seed를 사용한다.
- 심사자는 당사자 역할을 동시에 수행하지 않는다.
- 검토자와 변호자에게 상대방 초안을 미리 노출하지 않는다.
- 모든 역할의 모델, 프롬프트 버전, 증거 checksum을 audit한다.
